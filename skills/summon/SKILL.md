# /summon — 召唤词调度器

## 这个 Skill 是什么

一套 **20 个精选思想召唤词 + 7 条避雷区** 的词典。核心理念：**一个高浓度名词 = 一整套思想方法论的压缩包**，AI 听到名字就能激活整套思维框架，比长篇提示词更有效。

## 何时触发

**仅当用户输入以 `/summon` 开头的命令时触发**，不污染普通对话。

## 三种使用方式

### 方式 A：自动匹配（默认）

```
用户：/summon 帮我设计一个设置页面，别太花哨
```

AI 执行流程：
1. 读取 `dictionary.md` 和 `avoid-list.md`
2. 扫描需求关键词 → 识别场景
3. 按场景映射表挑选 3~5 个正向词 + 0-2 个避雷词
4. 检查冲突互斥
5. **先宣告**召唤词，再执行任务

响应格式：
```
> **◈ 召唤阵**
>
> ✦ **召唤词1** — 一句话作用
> ✦ **召唤词2** — 一句话作用
> ✦ **召唤词3** — 一句话作用
> ◇ ~~避雷词~~ — 一句话原因
```

宣告完毕后直接进入正文执行，不需要"开始执行..."过渡语。

### 方式 B：手动指定

```
用户：/summon 第一性原理 奥卡姆剃刀 | 帮我选数据库方案
```

- 分隔符 `|` 之前是手动指定的召唤词，之后是任务
- AI 只使用指定的词，不自动补充
- 仍需检查数量上限（超 5 个只用前 5 个）
- 如果 `|` 之前为空，回退到方式 A（自动匹配）
- 如果手动指定的词不在词典中，提示「⚠️ "XXX" 不在词典中，已忽略。使用 `/summon --list` 查看可用词」；如果所有手动词都无效，回退到方式 A
- 手动模式下不触发琐碎退出——用户显式指定召唤词表示明确意图

**词名匹配规则**：手动指定的词按**模糊匹配**识别——输入包含词典中某个词的核心关键词即可命中。例如：
- 输入 `Dieter Rams` 或 `Rams` → 命中「Dieter Rams 十诫」
- 输入 `原研哉` → 命中「原研哉的"白"」
- 输入 `80/20` 或 `帕累托` → 命中「80/20 法则（帕累托）」
- 输入 `Rubber Duck` → 命中「Rubber Duck Debugging」
- 输入 `乔布斯` 或 `Focus` → 命中「乔布斯的 Focus 哲学」

匹配优先级：完整词名 > 核心关键词 > 英文/中文别名。如果一个输入能匹配多个词，取最相关的那个。

### 方式 C：查看词典

```
用户：/summon --list
```

AI 读取 `dictionary.md` 和 `avoid-list.md`，以紧凑表格形式列出全部内容。

- 如果同时出现 `--list` 和需求文本，优先执行 `--list`，忽略需求部分

### 空输入处理

用户输入 `/summon` 但无需求时，回复简短用法提示：
> 用法：`/summon <需求>` | `/summon 词1 词2 | 需求` | `/summon --list`

## 自动匹配规则

### 匹配思路（给 AI 的指引）

**不要死板匹配关键词，要理解用户的任务性质。** 按以下优先级判断：

1. **先判断任务类型**：这个任务是在做"创造"（写文案/设计界面/定方案）还是"解决"（修 bug/排查问题/实现需求）？
   - 创造型任务 → 召唤词价值高，认真选
   - 解决型任务 → 召唤词价值低，可以少选甚至不选

2. **再判断发散度**：这个任务有多少种"都说得通"的做法？
   - 高发散（写品牌文案、做架构规划、反思决策）→ 选 3~5 个词帮用户定方向
   - 低发散（修一个具体 bug、实现一个明确需求）→ 选 0-1 个词就够

3. **最后从词典里选最贴切的**：读 `dictionary.md` 里每个词的「适用场景」和「反模式」字段，选和当前任务最匹配的。不要只看组名，要看具体场景描述。

### 场景 → 优先组映射（参考，非硬规则）

| 任务性质 | 优先组 | 可选叠加 |
|---------|--------|---------|
| 界面设计、视觉风格、用户体验 | 第二组（设计） | 第一组 1 个通用词 |
| 架构、选型、模块划分、重构、规划 | 第三组（工程） | 第一组 1 个通用词 |
| Bug 排查、性能问题、报错分析 | 第四组（调试） | 第一组 1 个通用词 |
| 文案、博客、文档、README、PR 描述 | 第五组（写作） | 第一组 1 个通用词 |
| 决策分析、方案对比、优先级排序 | 第一组（决策） | — |
| **跨领域 / 不确定** | 从第一组选 1 个通用词 + 最贴切的专业组选 1-2 个 | — |

### 避雷词自动映射（参考）

| 任务性质 | 优先避雷 |
|---------|---------|
| SaaS/产品首页/Landing Page | 不要硅谷独角兽风 |
| 工具型 UI / 设置页 / 极简风格 | 不要 MD3 浮夸阴影 |
| 中文产品 / 有字体设计需求 | 不要通用字体陈词滥调 |
| 文案 / 博客 / README | 不要 ChatGPT 味文风 |
| Java/OOP 重构 | 不要 Java 企业级抽象 |
| 防御性代码 / 错误处理 | 不要过度防御性编程 |
| 性能优化 / 架构选型 | 不要过早优化 |

### 组内选词规则

匹配到某一组后，不要随机选。读该组每个词的「适用场景」字段，选和用户当前任务**最贴切的**。例如：
- 同样是设计组，"设置页面要极简" → 选 Dieter Rams + 原研哉（克制+留白）
- 同样是设计组，"这个拖拽交互不太对" → 选 Polanyi 默会知识（直觉交互）
- 同样是设计组，"首页功能太多想砍" → 选乔布斯 Focus（砍功能）

### 数量与质量

- **正向词 3~5 个**（单一领域 3 个，跨域复杂任务可到 5 个），**避雷词最多 2 个**
- 超上限时砍尾部并宣告

### 琐碎任务退出

**答案没有设计空间的任务，不召唤，直接执行。** 判断标准：有多种"都说得通"的做法 → 值得召唤；答案基本唯一 → 直接做。拿不准时宁可召唤。

跳过时**必须简短告知用户**，不要静默跳过。一句话说明原因即可，例如：
> 💡 这个任务答案比较明确，召唤词帮不上太多忙，直接上手。

### 冲突与去重

- 词与用户需求矛盾时（如用户要"功能齐全"但选了乔布斯 Focus），不选该词
- 两个词方向矛盾时，保留与任务更贴切的那个，宣告冲突
- 多个词指向同一方向时（如 KISS + 奥卡姆 + YAGNI 都指向"简单"），只选最贴切的一个

## 对话内持续生效

**一次 `/summon` 在当前对话内持续生效，不需要每轮重复调用。**

规则：
- 用户在对话中首次调用 `/summon` 后，AI 记住当前召唤词
- 后续对话轮次中，如果用户的任务性质没有根本变化，继续沿用已召唤的词，**不需要再次宣告**
- 如果用户的任务性质发生根本变化（比如从"写文案"变成"排查 bug"），AI 应主动提示："当前召唤词是 X，这个任务可能更适合 Y，要切换吗？"
- 用户可以随时用新的 `/summon` 覆盖之前的召唤词

## 注意事项

- 召唤词是**方向舵**，不是发动机——AI 仍需完成具体任务
- 第一次使用某召唤词时，AI 应在执行中简短体现这个词的核心思想，方便用户对齐
- 任务执行完毕后，**不需要**再总结"我用了这些召唤词"——宣告一次就够
