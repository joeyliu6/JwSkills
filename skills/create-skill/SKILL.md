# Create Skill — 引导式技能创建

**好的 Skill = 一句方向 + AI 自身能力。这个工具确保你在脑子不清楚时也不会写出枷锁。**

---

## 触发

用户输入 `/create-skill` 或 `/create-skill 简要描述` 时执行。

---

## 三阶段流程

### Phase 1：采访（Discovery Interview）

通过 ~10 个问题理解用户想创建什么 skill。**每轮问 2-3 个，共 ~4 轮对话。** 不要一次性把所有问题丢给用户。

如果 `$ARGUMENTS` 已给出描述，跳过答案已明确的问题。根据用户回答灵活调整后续问题——如果前面的回答已经覆盖了后续问题，直接跳过。

#### 问题清单

| # | 问题 | 挖什么 |
|---|------|--------|
| 1 | 这个 skill 要解决什么问题？没有它时你怎么做？ | 明确 skill 的增量价值 |
| 2 | 谁会用？只有你，还是团队/开源用户也会用？ | 受众决定抽象层级和引导详细度 |
| 3 | 偏向"给 AI 补知识"还是"给 AI 定流程"？ | 知识型 vs 任务型，决定结构 |
| 4 | **AI 自己做不到的部分是什么？** 哪些信息从训练数据推断不出？ | **最关键** — 这是 skill 存在的理由 |
| 5 | 你想让 AI 关注哪几个"方向"？（一句话一个方向，不要列具体规则） | 强制方向性表达，防止枷锁 |
| 6 | 有什么 AI 绝对不能做的？（硬性禁忌） | 分离硬约束和软引导 |
| 7 | 自动触发还是只能手动 `/command`？什么场景触发？ | 决定 frontmatter 设置 |
| 8 | 有没有大量参考内容需要辅助文件？（词典、模板、示例库） | 决定文件结构 |
| 9 | 需要感知项目上下文吗？（如 project-config.md、package.json） | 决定是否加上下文检测 |
| 10 | 你踩过的坑或见过的反模式，是这个 skill 要防住的？ | 高价值内容，AI 推断不出 |

#### 采访节奏

- 第一轮：Q1 + Q2 + Q3（理解大方向）
- 第二轮：Q4 + Q5（挖核心价值——这两个最重要，单独一轮让用户充分思考）
- 第三轮：Q6 + Q7 + Q8（技术决策）
- 第四轮：Q9 + Q10（上下文和经验）

**诚实判断**：如果采访过程中发现用户想要的东西 AI 已经知道（Q4 答不出"AI 做不到的部分"），直接告诉用户："也许一句提示就够了，不一定需要完整 skill。" 不要为了创建而创建。

---

### Phase 2：生成（Draft Generation）

基于采访结果生成 skill 草稿。遵循以下方向：

#### 生成原则

1. **把采访答案映射为方向和结构，不是规则清单。** Q4/Q5 的回答应变成一句话方向，不是十条检查项。Q6 的硬性禁忌可以保留为明确条目。

2. **一句话测试。** 每个段落能不能压缩成对聪明同事说的一句话？能 → 用那句话。

3. **只保留 AI 推断不出来的部分。** 逐条审视：删掉这条，AI 还能做对吗？能 → 删掉。

4. **遵循仓库惯例：**
   - YAML frontmatter（name, description, 按需加其他字段）
   - `# English Name — 中文名` 标题格式
   - 一句话加粗核心理念
   - 表格用于结构化对比
   - 反模式节列出失败模式
   - 与其他 skill 配合节

5. **Frontmatter 决策：**
   - `description`：前置触发场景，用用户自己的话，≤250 字符
   - `disable-model-invocation`：Q7 说手动触发 → `true`
   - 其他字段按需（`context: fork`、`allowed-tools`、`agent` 等）

6. **辅助文件：** 如果 Q8 有大量参考内容，拆出辅助文件。SKILL.md 里写明辅助文件的用途和加载时机。

#### 生成产出

- SKILL.md 草稿（完整内容，可直接预览）
- 辅助文件草稿（如有）
- 文件结构说明

**不要直接写入文件。** 草稿和 Phase 3 自检结果一起呈现给用户审批。

---

### Phase 3：哲学自检（Philosophy Self-Check）

读取 `${CLAUDE_SKILL_DIR}/philosophy-checklist.md`，对草稿逐项检查。

#### 输出格式

```markdown
## 哲学自检结果

| 检查项 | 结果 | 详情 |
|--------|------|------|
| SKILL.md 行数 | ✅ / ⚠️ / ❌ | 具体行数 |
| 规则/条目数 | ✅ / ⚠️ / ❌ | 具体条数 + 建议 |
| Description 长度 | ✅ / ⚠️ / ❌ | 具体字符数 |
| 删除测试 | ✅ / ⚠️ | N 条可删，列出具体条目 |
| 方向 vs 枷锁 | ✅ / ❌ | N 条是枷锁，列出并建议改写 |
| 结构合理性 | ✅ / ⚠️ | 知识/任务分类、辅助文件合理性 |
```

- **⚠️ 警告项**：提出具体修改建议，用户决定是否采纳
- **❌ 阻断项**：必须修改后才能写入文件

将草稿 + 自检结果一起呈现给用户，等待审批。

---

## 写入文件

用户审批通过后：

1. 写入 `.claude/skills/<name>/SKILL.md`（及辅助文件）
2. 镜像到 `skills/<name>/`（内容完全一致）
3. 提醒用户更新 `CLAUDE.md` Skill 清单表格

```markdown
## 创建完成

| 文件 | 位置 |
|------|------|
| SKILL.md | .claude/skills/<name>/ + skills/<name>/ |
| [辅助文件] | .claude/skills/<name>/ + skills/<name>/ |

**测试**: 输入 `/<name>` 试用。
**别忘了**: 更新 CLAUDE.md 的 Skill 清单。
```

---

## 反模式

| 违规 | 为什么失败 |
|------|-----------|
| 跳过采访直接生成 | 没理解用户需求，生成的 skill 大概率不对 |
| 生成 20+ 条规则的 skill | 枷锁型——AI 变成逐条打勾的实习生 |
| 把 AI 已知的最佳实践写进 skill | 浪费 token，分散 AI 注意力 |
| 采访时替用户回答 | 用户的领域知识和踩坑经验才是 skill 的核心价值 |
| 自检全部通过但草稿空洞 | 通过自检 ≠ 好 skill——内容必须有实质价值 |

## 与其他 skill 的配合

- **`/summon`**：创建前用 summon 定思维方向（如"第一性原理"帮助想清楚 skill 到底要解决什么）
- **`/triple-check`**：对生成的 skill 做三轮自检（适用于复杂 skill）
- **`/init-skills`**：如果新 skill 需要 project-config 支持，创建后运行 init-skills 更新配置

---

## 记住

> 你是在帮用户提炼**他知道但 AI 不知道的东西**。
> 如果采访结束后发现没什么 AI 不知道的，诚实说出来——不创建比创建一个无用 skill 更好。

**方向而非枷锁，对生成器自身也适用。**
