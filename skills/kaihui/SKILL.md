# Kaihui — 开会：工作流编排器

**你是项目经理，不是执行者。分配任务、评判产出、推进流程——直到交付。**

---

## 核心理念

用户脑子里有一套"该从哪些角度、用什么工具、按什么顺序处理问题"的经验，
但每次都要手动一步步告诉 AI。Kaihui 把这套经验固化成**可复用的 workflow 模板**。

每个 workflow 是一条流水线：`步骤 → 评判 → 步骤 → 评判 → ... → 收敛交付`

---

## 触发

用户输入 `/kaihui` 时执行。

### 三种用法

| 用法 | 示例 |
|------|------|
| 自动选模板 | `/kaihui 帮我设计一个新的上传队列功能` |
| 指定模板 | `/kaihui #深度分析 这个性能问题怎么优化` |
| 管理模板 | `/kaihui --list`、`/kaihui --show 模板名` |

---

## 执行流程

### Step 0：选择 Workflow

1. 读取 `workflows.md`
2. **自动模式**：根据任务性质匹配最合适的 workflow，向用户展示选择理由
3. **指定模式**（`#模板名`）：直接使用指定模板
4. **无匹配时**：根据任务性质和已有技能，现场组合一个临时 workflow，展示给用户确认

```markdown
> **📋 会议议程：[workflow 名]**
>
> 1. [步骤1名] — 一句话目的
> 2. [步骤2名] — 一句话目的
> 3. ...
> 
> 预计 N 个步骤，每步产出后评判确认再推进。
> 确认开始？
```

用户确认后开始执行。

### Step 1~N：逐步执行

每个步骤按以下节奏执行：

**执行 → 产出 → 评判 → 用户确认 → 下一步**

#### 执行

- 步骤指定了技能（如 `/summon`、`/triple-check`）→ 调用该技能
- 步骤指定了视角（如"站在产品经理角度"）→ 切换到该视角思考
- 步骤指定了动作（如"联网搜索最佳实践"）→ 执行该动作

#### 步骤结束格式（强制）

每步执行完后，必须按以下**完整顺序**输出三部分，缺一不可：

**第一部分 — 步骤结果**（参照 PROTOCOL.md）：

```markdown
### 步骤 N/M：[步骤名]

- **状态**：✅ PASS | ❌ FAIL | ⚠️ NEED_REVIEW | ⏭️ SKIP
- **产出摘要**：[一句话描述这步做了什么，不能只说"已完成"]
- **修改的文件**：[文件路径列表，没有则写"无"]
- **遗留问题**：[未解决的问题，没有则写"无"]
```

**第二部分 — 评判**：

```markdown
> **📊 评判**
> - 质量：✅ 充分 / ⚠️ 部分不足 / ❌ 需重做
> - 发现：[关键发现，必须 ≥15 字，见"评判反走过场"规则]
> - 衔接：[与前序步骤的关系，是否有矛盾/遗漏]
> - 建议：继续 / 补充 / 重做
```

**第三部分 — 等待确认**（⛔ 绝对红线第 1 条）：

```
确认继续下一步？（可选：继续 / 补充 / 跳过 / 插入）
```

输出此行后**必须停止**，等待用户回复。用户可以：
- **继续**：进入下一步
- **补充**：对当前步骤追加要求，重新执行
- **跳过**：跳过后续某步骤
- **插入**：在流程中插入新步骤

### 收敛交付（最后一步固定格式）

最后一步始终是**收敛**，必须使用以下结构化模板：

```markdown
## 🎯 Kaihui 会议结束 - 最终交付

### 会议回顾
| 步骤 | 状态 | 关键产出 |
|------|------|---------|
| 1. [步骤名] | ✅/❌/⚠️/⏭️ | [一句话核心产出] |
| 2. [步骤名] | ✅/❌/⚠️/⏭️ | [一句话核心产出] |
| ... | ... | ... |

### 步骤间关系检查
- [步骤 A] vs [步骤 B]：[一致/矛盾/互补，具体说明]
- 遗留问题汇总：[从各步骤的"遗留问题"中汇总，没有则写"无"]

### 最终交付物
[具体交付内容——代码、方案、结论等]

### 未解决事项
[列出需要用户后续决策的事项，没有则写"无"]
```

收敛步的核心职责：
1. **综合所有步骤**的产出和评判，不能只取最后一步的结论
2. **处理步骤间的矛盾**（不同角度可能给出相反建议）
3. 如有未解决的矛盾，**明确列出**让用户决策

## 防坑机制

关注以下四个方向（从 AI workflow 编排的常见失败模式提炼）：

| 方向 | 说明 |
|------|------|
| **角色隔离** | 每步切换视角时，不被前一步的措辞带跑 |
| **错误阻断** | 评判发现问题时阻断推进，不把错误传递给下游 |
| **输出压缩** | 每步产出结构化、精炼，不让上下文膨胀失控 |
| **矛盾收敛** | 不同角度的结论矛盾时，在收敛步明确处理而非忽略 |

---

## 评判反走过场

评判是 kaihui 的核心价值，不能沦为形式：

- **"发现"字段必须有具体内容**（≥15 字），不能只写"无"或"没有问题"
- 如果真的没有问题，写明"已检查 [具体检查项]，均无异常"——证明你确实检查过
- **连续 3 步都是 ✅ 充分时**，第 3 步必须额外说明为什么确信没有遗漏
- 评判必须基于本步骤的**实际产出**，不能泛泛而谈

---

## 工具降级

当步骤执行中必要的工具（如 `git diff`、`git status`）不可用时：

1. **明确告知用户**：「⚠️ [工具名] 不可用，本步骤结果可能不完整」
2. **状态标记为 ⚠️ NEED_REVIEW**，而非 ✅ PASS
3. **在评判中注明信息缺失的影响**，不能假装没问题继续

---

## 模板管理

### 查看模板

`/kaihui --list` → 列出所有 workflow 模板名 + 一句话用途

`/kaihui --show 模板名` → 展示该模板的完整步骤

### 保存新模板

当 AI 现场组合了临时 workflow，用户满意后可以说"保存为新模板"。
AI 将新模板追加到 `workflows.md`，格式与内置模板一致。

### 编辑模板

用户可以随时要求修改 `workflows.md` 中的模板——增删步骤、调整顺序、改变视角。

---

## ⛔ 绝对红线（违反即流程无效）

1. **每步评判后必须暂停等用户确认** — 不能自动推进到下一步。输出评判后，必须以「确认继续？（可选：继续 / 补充 / 跳过 / 插入）」结尾，然后**停止输出**，等待用户回复。这是 kaihui 最核心的价值——用户在每个节点有决策权
2. **不能跳过评判步骤** — 每步产出后必须评判，用户必须能看到
3. **不能在用户未确认方案时写代码** — 涉及编码的步骤，方案确认后才执行
4. **不能静默吞掉矛盾** — 步骤间的矛盾必须显式呈现给用户
5. **不能静默跳过步骤** — 如果某步无需执行，必须输出 ⏭️ SKIP 状态和跳过原因，仍需用户确认

---

## 反模式

| 违规 | 为什么失败 |
|------|-----------|
| 一次性执行所有步骤 | 失去逐步评判的价值，用户无法介入 |
| 评判全是"✅ 充分" | 走过场——评判必须有实质内容 |
| 后续步骤复述前序产出 | 上下文膨胀——引用结论，不复述过程 |
| 收敛时只取最后一步的结论 | 浪费了多角度的价值，必须综合所有步骤 |

## 与其他 skill 的配合

Kaihui 是其他 skill 的**上游编排器**：

- **`/summon`**：作为 workflow 步骤中的"视角召唤"环节
- **`/plan-before-code`**：作为"设计"步骤
- **`/triple-check`**：作为"高质量实现"步骤
- **`/code-review`**：作为"审查"步骤
- **`/code-simplifier`**：作为"代码简化"步骤
- **`/create-skill`**：保存新模板时，如果模板足够通用，可建议升级为独立 skill

### 技能名称精确匹配（⛔ 强制）

用户在任务描述中提到的技能名，必须**精确匹配**项目 `.claude/skills/` 下的自定义技能：

- 用户说 "code-simplifier" → 必须调用 `/code-simplifier`，**不能**替换为内置的 `/simplify`
- 用户说 "code-review" → 必须调用 `/code-review`
- 如果名称模糊（如"简化代码"），**优先匹配项目自定义技能**，其次才考虑内置技能
- 如果无法确定，在 Step 0 展示 workflow 时明确标注将调用哪个技能，让用户确认
