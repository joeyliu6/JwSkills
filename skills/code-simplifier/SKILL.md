# Code Simplifier — 代码简化器

**简化 = 让下一个读代码的人更快理解，同时一个行为都不变。**

---

## 核心方向

### 功能零变更（硬约束）

绝不改变代码的可观测行为。包括：返回值、副作用、错误抛出、日志输出、事件触发顺序。

如有疑问，不动。

### 关注三个方向

1. **可读性** — 减少认知负担：嵌套层级、命名含糊、逻辑绕弯
2. **冗余** — 删除无用代码、废话注释、过度封装
3. **一致性** — 遵循项目已有的风格和约定（从 CLAUDE.md 读取）

### 不能动的东西（AI 盲区）

这是 AI 简化代码时最容易犯的错——以下场景必须保留原样：

- **防御性代码**：看似"不可能到达"的 guard clause，往往是踩过坑后加的
- **有意重复**：两段相似代码可能故意分开，因为未来会分化——不要急着 DRY
- **隐式契约**：错误消息的精确文本、日志格式、事件触发顺序，下游可能依赖
- **性能相关的写法**：看起来"不优雅"但有性能原因的代码（如手动循环 vs 链式 map/filter）

拿不准时问用户，不要自行判断删除。

---

## 工作范围

- **默认只动最近修改的代码**（通过 git diff 识别）
- 不要连带"顺手"重构未改动的代码
- 每次简化后用一句话说明改了什么、为什么

---

## 反模式

| 做了这个就错了 | 为什么 |
|---------------|--------|
| 删掉看似多余的 null 检查 | 可能守护了罕见但真实的边界条件 |
| 把两段相似逻辑合并成一个泛化函数 | 过度抽象——三次重复前不要 DRY |
| 改完不验证行为一致 | 简化的全部价值建立在行为不变之上 |
| 简化了调用链上游/下游未读过的代码 | 上下文窗口看不到的地方不要动 |
| 为了少几行代码牺牲可读性 | 简化是为了清晰，不是为了短 |

## 与其他 skill 的配合

- **`/code-review`**：简化完后跑一轮 review，确保没引入问题
