# Plan Before Code — 先设计后编码

**改流程图一行字 = 改代码半小时。设计阶段是最廉价的 debug。**

---

## 核心原则

> AI 默认行为：拿到需求就开始写代码——一个文件写到底，只走 happy path，功能交界处全是 bug。
> 本 skill 强制在写代码前完成三阶段设计，用**审核设计图的时间**换**返工改代码的时间**。

---

## 触发时机

### 显式触发
用户输入 `/plan-before-code $ARGUMENTS` 时立即按流程执行。

### 关键词触发（主动建议）
用户说这些词时，建议启用：
- "新功能"、"从零开始"、"完整实现"
- "先设计"、"先规划"、"画个流程图"
- "多模块"、"全栈"、"系统化"

### 复杂度阈值
任务涉及 **新建 3+ 文件**、**引入新数据模型**、**跨越前后端**、或**大规模重构（重新设计架构/数据层/模块边界）** 时，应主动建议启用。

---

## 三阶段执行流程

**每个阶段产出后，等用户确认再进入下一阶段。** 用户可以在任何阶段打回修改。

### Phase 1：架构骨架

目标：想清楚"有哪些模块、谁依赖谁"。

产出：
- **模块拆分**：每个文件/模块的职责（一句话说清）
- **数据结构**：核心类型/接口定义（用项目对应语言写）
- **依赖关系**：Mermaid 图展示模块间的依赖

```markdown
## Phase 1：架构骨架

### 模块拆分
| 文件 | 职责 |
|------|------|
| ... | ... |

### 核心数据结构
[类型/接口定义]

### 依赖关系
```mermaid
graph TD
  A[模块A] --> B[模块B]
  A --> C[模块C]
`` `

等待用户确认后进入 Phase 2。
```

### Phase 2：流程与状态

目标：想清楚"用户怎么走、状态怎么变"。

产出：
- **用户流程**：每个用户交互的 Mermaid 流程图（含异常路径，不只是 happy path）
- **状态机**：有状态的组件用 Mermaid stateDiagram 展示所有状态和转换条件
- **API 契约**（如涉及）：请求/响应格式

```markdown
## Phase 2：流程与状态

### 用户流程
```mermaid
flowchart TD
  Start[用户操作] --> Check{条件}
  Check -->|成功| Success[成功状态]
  Check -->|失败| Error[错误处理]
  Error --> Retry[重试/回退]
`` `

### 状态机
```mermaid
stateDiagram-v2
  [*] --> Idle
  Idle --> Loading: 触发
  Loading --> Success: 成功
  Loading --> Error: 失败
  Error --> Loading: 重试
`` `

等待用户确认后进入 Phase 3。
```

### Phase 3：边界清单

目标：强制枚举"什么地方会出问题"。

**按以下 7 个方向检查**（这些是方向，不是逐条打勾的清单——根据任务实际情况判断哪些方向最关键，深入那些方向）：

| 方向 | 关注点 |
|------|--------|
| **中断** | 用户取消、离开页面、刷新、关闭标签 |
| **空值/缺失** | 无数据、首次使用、已删除内容、过期会话 |
| **错误状态** | 网络失败、API 错误、超时、权限不足 |
| **并发** | 双击、并行请求、过期数据、乐观更新 |
| **规模** | 0/1/100/10000 条数据时的表现 |
| **跨功能** | 新功能与现有功能在边界处的交互 |
| **状态转换** | 状态机每个入口/出口是否完整、有无不可达状态 |

**强制输出**：具体场景 + 预期行为 + 处理方式（不是"可能有问题"这种空话）。

```markdown
## Phase 3：边界清单

| 方向 | 场景 | 预期行为 | 处理方式 |
|------|------|---------|---------|
| 中断 | 上传中途关闭页面 | 上传取消，不留残余文件 | beforeunload 提示 + 服务端清理 |
| 空值 | 首次使用无数据 | 显示空状态引导 | EmptyState 组件 |
| ... | ... | ... | ... |

等待用户确认。
```

## 设计文档合并

三个阶段全部通过后，输出合并的设计文档：

```markdown
## 设计文档：[功能名]

### 架构骨架
[Phase 1 产出]

### 流程与状态
[Phase 2 产出]

### 边界清单
[Phase 3 产出]

### 实现计划
| 顺序 | 模块 | 依赖 | 复杂度 |
|------|------|------|--------|
| 1 | ... | 无 | 低 |
| 2 | ... | 模块1 | 中 |

> 建议按顺序逐个用 `/triple-check` 实现每个模块。
```

---

## 反模式（阻断）

| 违规 | 为什么失败 |
|------|-----------|
| 跳过 Phase 直接写代码 | 失去设计审核的价值，回到"写了再改"的老路 |
| 流程图只画 happy path | 没解决核心问题——异常路径必须出现在图里 |
| 边界清单全是空话 | "可能会有性能问题"没有价值，必须具体到场景和处理方式 |
| 三个 Phase 一次性全输出 | 失去门控审核的价值，用户来不及消化 |

---

## 何时不该用

| 场景 | 原因 |
|------|------|
| Bug 修复 | 架构已有，直接改代码 |
| 单文件改动 | 无架构决策 |
| 小范围重构（拆函数、改命名） | 结构已存在，在现有结构上改 |
| 探索/原型 | 设计文档 for 扔掉的代码是浪费 |
| 需求不清楚 | 先澄清需求，设计什么都不知道 |
| 样式/CSS 调整 | 无架构决策 |

遇到这些场景时，直接告知用户原因并正常执行任务。

## 与其他 skill 的配合

- **`/triple-check`**：plan-before-code 输出设计文档，triple-check 按模块高质量实现——**设计 + 实现双保险**
- **`/summon`**：先用 summon 定思维方向，再用 plan-before-code 做系统设计
- **`/code-review`**：实现完成后用 code-review 做最终审查

**完整链条**：`/summon` → `/plan-before-code` → `/triple-check`（逐模块）→ `/code-review`

---

## 记住

> 你不是在画图玩。每一阶段都要产出用户能审核的具体设计。
> 如果边界清单里找不到一条具体场景，说明你偷懒了，重新来过。

**设计不是目的，避免返工才是。**
