# /code-review — 系统代码审查

> 宁可漏报 3 个小毛病，不可误报 1 个不存在的 bug。
> 信噪比至上——开发者被噪音淹没后会无视所有反馈。

## 快速上手

```bash
# 用户级
cp -r code-review/ ~/.claude/skills/

# 或项目级
cp -r code-review/ /path/to/your-project/.claude/skills/
```

使用：

```
/code-review 审查这个 PR 的变更
```

AI 会按 6 步流程执行：
1. **快速扫描** — 理解变更意图和范围
2. **深度审查** — 按清单逐项检查，产出粗筛列表
3. **半形式化推理** — 逐条追踪代码路径验证（Meta 研究启发）
4. **置信度标注** — 过滤推测性发现
5. **优先级截断** — 按变更规模限制发现数量
6. **终审验证** — 回源码确认行号和逻辑

## 为什么这样设计

### Meta "Agentic Code Reasoning" 启发

Meta 2026 年研究发现：要求 AI 填写**逻辑证书**（前提假设 → 执行路径追踪 → 防护检查 → 触发条件 → 结论），准确率从 86% 提升到 93%。

本技能实现了同样的思想：每条发现必须通过推理表格验证，不准直觉判断。这是和朴素的"列出所有问题"方法最关键的区别。

### 信噪比哲学

优先级金字塔（安全 > 正确性 > 性能 > 可维护性 > 风格）+ 三层过滤（推理验证 → 置信度标注 → 优先级截断）确保只有**已验证的高影响问题**出现在最终报告中。

最重要的规则：**推测性发现全部移除，不输出。** 一个误报的伤害远大于三个漏报——因为开发者被噪音训练出"无视 AI review"的习惯后，真正的关键问题也会被忽略。

## 适用场景

✅ **用**：
- PR review（代码审查请求）
- 重构后的质量审计
- 关键路径代码的安全审查
- 合并前的最终检查

❌ **不用**：
- 纯风格争论（用 linter）
- 需求讨论（先搞清楚做什么再审怎么做）
- 自动生成的代码（配置文件、迁移文件等）
- 上下文窗口吃紧时（6 步流程输出较长）

## 为你的项目定制

### 推荐方式：一键定制

安装技能后运行一次：

```
/init-skills
```

AI 会自动扫描项目技术栈，生成 `project-config.md`，包含你的框架、语言、UI 库对应的专项检查。详见 [init-skills README](../init-skills/README.md)。

### 手动方式

也可以直接在技能目录下创建 `project-config.md`，写入你的项目特有规则。格式参考 `/init-skills` 生成的模板。

## 成本权衡

⚠️ 注意：
- 6 步流程比简单"找问题"多消耗 **2-3x** token
- Step 3 的推理表格是内部过程（不输出给用户），但仍消耗 token
- 大 PR（500+ 行 diff）即使截断到 12 条，审查过程本身也较长

**权衡**：用 token 换**误报率的大幅降低**。一个误报的伤害 > 三个漏报——因为开发者被噪音训练出"无视 AI review"的习惯后，真正的关键问题也会被忽略。
