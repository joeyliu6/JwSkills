# /triple-check — 三遍自纠

> 一次交卷 = 学生答题；三遍自纠 = 工程师工作流。
> 用 token 换用户的返工精力。

## 快速上手

```bash
# 用户级
cp -r triple-check/ ~/.claude/skills/

# 或项目级
cp -r triple-check/ /path/to/your-project/.claude/skills/
```

使用：

```
/triple-check 按这份设计稿实现设置面板，所有边界态要覆盖
```

AI 会强制走三轮：
- **Round 1**：初版实现（覆盖 happy path）
- **Round 2**：边界压测反思（空值/超大数据/并发/非法输入/...）
- **Round 3**：规范审查反思（命名/类型/样式/项目约定）
- **汇总对比**：让改进幅度可审查

## 为什么这样设计

LLM 默认**贪心解码**——每次挑最可能的下一个 token，首次输出 = 训练数据里最常见的解法。这意味着：

- 边界情况 = 训练样本少 = 默认不会主动想到
- 没有外部反馈，模型不会自己"醒过来"

三遍自纠本质是：**把资深工程师的内心独白翻译出来，强制 AI 跑一遍**。

## 四大机制

每一条都在对抗 LLM 的某个默认行为：

| 要素 | 打破的默认行为 | 本质作用 |
|------|--------------|---------|
| **自行纠正三遍** | 一次输出就交卷 | 强制"生成→批评→修订"循环 |
| **模拟几万条数据测试** | 只考虑 happy path | 数量级锚定，逼出 edge case |
| **每次反思都要看到** | 偷懒跳过推理直接给答案 | 把思考从 hidden 变成 visible |
| **最终汇总对比** | 丢失中间过程价值 | 让用户看到改进幅度 |

## 适用场景

✅ **用**：
- 按设计稿/规范实现复杂 UI 或组件
- 重构核心模块（类型定义、核心接口、数据库层）
- 涉及多状态的功能（loading/error/empty/success/边界态）
- 数据处理、迁移、大数据量场景
- 任何"不能漏、不能错"的生产代码

❌ **不用**：
- 纯探索（"XX 是怎么工作的"）— 没有可验证的答案
- 单行 typo 修复 — 杀鸡用牛刀
- 需求本身没想清楚 — 越纠越偏
- 紧急 hotfix — 优先解决问题
- 上下文窗口吃紧 — 三轮输出会挤掉关键信息

## 为你的项目定制

### 推荐方式：一键定制

安装技能后运行一次：

```
/init-skills
```

AI 会自动扫描项目技术栈，生成 `project-config.md`，包含 Round 3 的项目专属检查规则。详见 [init-skills README](../init-skills/README.md)。

### 手动方式

也可以直接在技能目录下创建 `project-config.md`，写入你的项目特有规则。格式参考 `/init-skills` 生成的模板。真实项目案例见 [../../examples/picnexus-triple-check.md](../../examples/picnexus-triple-check.md)。

## 成本权衡

⚠️ 不是银弹：
- Token 消耗 **3-5x** 普通任务
- 需求模糊时，三遍只会越纠越偏
- 超出模型能力时，纠 10 遍也没用

⚠️ 成瘾风险：
- 用户习惯"反正 AI 会自纠"后，可能懒得自己想清楚需求
- 把思考外包给 AI 是危险的

**权衡**：节省的是**用户的返工精力**，代价是**模型的 token**。对注意力有限的开发者来说，通常划算。
