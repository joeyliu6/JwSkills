# Triple-Check - 三遍自纠

**一次交卷 = 学生答题；三遍自纠 = 工程师工作流**

---

## 核心原则

> LLM 默认贪心解码——首次输出就是训练数据里最常见的解法，必然漏边界。
> 本 skill 强制走三轮审慎工作流，用 token 换**用户的返工精力**。

---

## 触发时机

### 显式触发
用户输入 `/triple-check <任务描述>` 时立即按流程执行。

### 关键词触发（主动建议）
用户说这些词时，建议启用：
- "按此代码改"、"按设计稿实现"、"按此规范"
- "必须正确"、"不能漏"、"不能出错"、"一次到位"
- "考虑所有边界"、"完整覆盖"

### 复杂度阈值（可选）
改动 > 3 文件、涉及项目核心模块（按你的项目列出，如类型定义/核心接口/数据库层）时可主动建议。

---

## 三轮执行流程

### Round 1：初版实现

- 按需求直接产出代码/方案
- 覆盖主路径（happy path）
- 匹配现有代码风格
- 不要在本轮纠结边界——先跑起来

### Round 2：边界压测反思

**对自己的 Round 1 产出做极端输入测试**，具体列举：

| 维度 | 检查项 |
|------|--------|
| **空值/零值** | 空字符串、空数组、空对象、0、null、undefined |
| **超大数据量** | 几万条、几十万条记录时的性能、内存、渲染 |
| **非法输入** | 特殊字符、超长字符串、SQL/XSS 注入、异常编码 |
| **边界值** | 最大值、最小值、负数、浮点精度、时间边界 |
| **并发/异步** | 多次点击、网络异常、请求中断、竞态条件 |
| **外部依赖** | API 失败、超时、离线、权限缺失、磁盘满 |
| **状态组合** | loading/error/empty/success 所有分支 |

**强制输出**：列出每条**具体发现的问题**（不是"可能有问题"这种空话），然后给出修订后代码。

### Round 3：规范审查反思

**按项目约定文档（CLAUDE.md / CONTRIBUTING.md / 团队风格指南）+ 现有代码风格审查**，具体列举：

| 维度 | 检查项 |
|------|--------|
| **命名** | 遵循项目命名约定（如 camelCase/PascalCase/SCREAMING_SNAKE，布尔 is/has/can 前缀） |
| **函数** | 长度与参数数量限制，提前返回减少嵌套 |
| **类型** | 禁止 `any`，完整类型标注（TypeScript 项目） |
| **注释** | 只解释"为什么"，无废话注释、无注释掉的代码 |
| **样式** | 项目的 CSS 变量/UI 库约定（禁止硬编码颜色/魔法数字） |
| **语言** | 项目语言约定（中文/英文/双语注释与文档） |
| **项目约定** | 匹配项目依赖图，不破坏高风险文件 |

**强制输出**：列出每条**具体不符合项**，然后给出最终代码。

> 💡 使用建议：在你的项目里，把上表的"检查项"替换成项目实际规范（例如："禁止硬编码颜色，必须用 `var(--xxx)`"、"函数 ≤20 行"、"禁止 `console.log` 进生产"）。规则越具体，Round 3 越有威力。

---

## 输出格式（强制）

```markdown
## Round 1：初版实现

[代码/方案]

---

## Round 2：边界压测反思

发现的问题：
1. 空输入时 xxx 会崩溃 — 原因: ...
2. 一万条数据时 xxx 会 xxx — 原因: ...
3. 并发场景下 xxx — 原因: ...

修订后代码：
[代码]

---

## Round 3：规范审查反思

不符合项：
1. 函数 xxx 超过 N 行 — 应拆分为 ...
2. 硬编码了颜色 `#xxx` — 应使用 `var(--xxx)`
3. 缺少 TypeScript 类型标注 — ...

最终代码：
[代码]

---

## 汇总对比

| 轮次 | 新增改进 | 覆盖的边界/规范 |
|------|----------|----------------|
| Round 1 | 主路径实现 | happy path |
| Round 2 | 修复 N 个边界 bug | 空值/大数据/并发/... |
| Round 3 | 规范化 M 处 | 命名/样式变量/类型/... |

**最终产出**：见 Round 3 的"最终代码"部分。
```

## 反模式（阻断）

| 违规 | 为什么失败 |
|------|-----------|
| 三轮输出雷同 | 没真的批评自己，假装跑流程 |
| 跳过反思直接给最终代码 | 失去审查价值，用户看不到改进过程 |
| 反思里全是空话 | "可以更健壮"没有价值，必须具体到"空数组会 NPE" |
| Round 2 只列 1-2 条问题 | 压测深度不够，至少要覆盖 3-5 个维度 |
| Round 3 只说"符合规范" | 没真审，必须列具体检查项 |
| 汇总表空洞 | 汇总是对三轮差异的自我认知，不能省 |

---

## 何时不该用

| 场景 | 原因 |
|------|------|
| 纯探索（"XX 是怎么工作的"） | 没有可验证的"正确答案" |
| 单行 typo 修复 | 杀鸡用牛刀 |
| 需求本身没想清楚 | 越纠越偏，先澄清需求 |
| 紧急 hotfix | 优先解决问题，不求完美 |
| 上下文窗口吃紧 | 三轮输出会挤掉关键信息 |

遇到这些场景时，直接拒绝执行并告知用户原因。

## 与其他 skill 的配合

| 配合对象 | 分工 |
|----------|------|
| 深度工作 skill | 负责深度探索 + 干到完整个任务链；triple-check 负责**单次产出**的质量 |
| 验证 skill | triple-check 是**写之前**的审慎（三轮反思）；verification 是**写之后**的证据（实际运行验证） |
| 规划 skill | planner 负责任务拆解；triple-check 负责每个拆出来的子任务的实现质量 |
| 架构 skill | oracle 负责架构决策；triple-check 负责把决策落地时不留死角 |

**最佳组合**：先拆任务 → 每个子任务用 `/triple-check` 实现 → 最后收证据验证。

---

## 记住

> 你不是在跑形式。每一轮都要真的批评自己、真的列出问题。
> 如果 Round 2 和 Round 1 看起来一样，说明你偷懒了，重新来过。

**三遍不是目的，覆盖边界才是。**
