# Triple-Check - 三遍自纠

**一次交卷 = 学生答题；三遍自纠 = 工程师工作流**

> **⚙️ 首次使用检测**：执行前，检查同目录下是否存在 `project-config.md`。
> - **不存在** → 提示用户："建议先运行 `/init-skills` 生成项目专属规则。现在继续将使用通用规则。"然后继续执行。
> - **存在** → 读取并应用其中的规则。

---

## 核心原则

> LLM 默认贪心解码——首次输出就是训练数据里最常见的解法，必然漏边界。
> 本 skill 强制走三轮审慎工作流，用 token 换**用户的返工精力**。

---

## 触发时机

### 显式触发
用户输入 `/triple-check <任务描述>` 时立即按流程执行。

### 关键词触发（主动建议）
用户说这些词时，建议启用：
- "按此代码改"、"按设计稿实现"、"按此规范"
- "必须正确"、"不能漏"、"不能出错"、"一次到位"
- "考虑所有边界"、"完整覆盖"

### 复杂度阈值
改动 > 3 文件、或涉及项目核心模块（按你的项目列出，如类型定义/核心接口/数据库层）时，**应主动建议启用**。

### 任务粒度守卫
单次 triple-check 应聚焦**单个功能或模块**。如果任务明显涉及多个独立子系统（如"全栈 CRUD + 权限 + 迁移"），先建议拆分再逐个 triple-check，否则三轮流程会变成走马观花。

---

## 三轮执行流程

### Round 1：初版实现

- 按需求直接产出代码/方案
- 覆盖主路径（happy path）
- 匹配现有代码风格
- 不要在本轮纠结边界——先跑起来

### Round 2：边界压测反思

**对自己的 Round 1 产出做极端输入测试。** 关注这些方向：

- **空值与边界值** — 代码遇到空/零/极大/极小输入时会怎样？
- **异常与故障** — 网络断开、API 超时、并发竞态、外部依赖失败时会怎样？
- **安全** — 有没有未校验的外部输入、敏感数据暴露、注入风险？
- **状态组合** — 所有状态分支（loading/error/empty/success）都覆盖了吗？

以上是方向指引，不是逐条打勾的清单。根据任务的实际场景判断哪些维度最关键，深入测试那些维度。

**强制输出**：列出每条**具体发现的问题**（不是"可能有问题"这种空话），然后给出修订后代码。

### Round 3：规范审查反思

**按项目约定文档（CLAUDE.md / CONTRIBUTING.md / 团队风格指南）+ 现有代码风格审查。**

> 📋 如果同目录下存在 `project-config.md`，读取其中的项目专属关注点，**追加到审查范围中**。项目专属规则优先级高于通用判断。

审查方向：
- **命名与风格** — 是否匹配项目现有的命名和代码风格？
- **类型与安全** — 类型标注是否完整？有无类型逃逸？
- **项目约定** — 是否遵循 CLAUDE.md 中的约束？是否与项目依赖和架构兼容？
- **无障碍**（前端项目）— 键盘导航、ARIA、色彩对比度

这些是方向，不是清单。根据项目实际情况和 `project-config.md` 中的专属规则来审查。

**强制输出**：列出每条**具体不符合项**，然后给出最终代码。

## 输出格式（强制）

```markdown
## Round 1：初版实现

[代码/方案]

---

## Round 2：边界压测反思

发现的问题：
1. 空输入时 xxx 会崩溃 — 原因: ...
2. 一万条数据时 xxx 会 xxx — 原因: ...
3. 并发场景下 xxx — 原因: ...

修订后代码：
[代码]

---

## Round 3：规范审查反思

不符合项：
1. 函数 xxx 超过 N 行 — 应拆分为 ...
2. 硬编码了颜色 `#xxx` — 应使用 `var(--xxx)`
3. 缺少 TypeScript 类型标注 — ...

最终代码：
[代码]

---

## 汇总对比

| 轮次 | 新增改进 | 覆盖的边界/规范 |
|------|----------|----------------|
| Round 1 | 主路径实现 | happy path |
| Round 2 | 修复 N 个边界 bug | 空值/大数据/并发/... |
| Round 3 | 规范化 M 处 | 命名/样式变量/类型/... |

**最终产出**：见 Round 3 的"最终代码"部分。
```

## 反模式（阻断）

| 违规 | 为什么失败 |
|------|-----------|
| 三轮输出雷同 | 没真的批评自己，假装跑流程 |
| 跳过反思直接给最终代码 | 失去审查价值，用户看不到改进过程 |
| 反思里全是空话 | "可以更健壮"没有价值，必须具体到"空数组会 NPE" |
| Round 2 只列 1-2 条问题 | 压测深度不够，至少要覆盖 3-5 个维度 |
| Round 3 只说"符合规范" | 没真审，必须逐条列出检查项及结论（通过/不通过+原因）。如确实全部合规，列出已检查通过的项证明你真的审过 |
| 汇总表空洞 | 汇总是对三轮差异的自我认知，不能省 |

## 何时不该用

| 场景 | 原因 |
|------|------|
| 纯探索（"XX 是怎么工作的"） | 没有可验证的"正确答案" |
| 单行 typo 修复 | 杀鸡用牛刀 |
| 需求本身没想清楚 | 越纠越偏，先澄清需求 |
| 紧急 hotfix | 优先解决问题，不求完美 |
| 上下文窗口吃紧 | 三轮输出会挤掉关键信息 |

遇到这些场景时，直接拒绝执行并告知用户原因。

## 与其他 skill 的配合

- **`/plan-before-code`**：plan-before-code 是**写代码前**的系统设计（架构 + 流程 + 边界）；triple-check 是**写代码时**的审慎实现——**设计 + 实现双保险**
- **`/code-review`**：triple-check 是**写代码时**的审慎（三轮反思）；code-review 是**写完后**的同行审查
- **`/summon`**：先用 summon 定方向，再用 triple-check 实现——方向 + 质量双保险

**完整链条**：`/summon` → `/plan-before-code` → `/triple-check`（逐模块）→ `/code-review`

**最佳实践**：复杂任务先用 `/plan-before-code` 做设计，再按实现计划逐模块用 `/triple-check` 实现。

---

## 记住

> 你不是在跑形式。每一轮都要真的批评自己、真的列出问题。
> 如果 Round 2 和 Round 1 看起来一样，说明你偷懒了，重新来过。

**三遍不是目的，覆盖边界才是。**
