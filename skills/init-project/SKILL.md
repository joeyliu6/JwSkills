# Init Project — 项目基线安装

**把规矩真装进项目，而不是再写一份等人来读的文档。**

模板文档的问题是它要人照着抄，抄到第三步就烦了——新项目粗糙就是这么来的。
这个技能负责执行那几步。

## 何时用

用户敲 `/init-project` 时用。**更重要的是不等他敲**——看到这些情况自己主动上：

- 新建的仓库，还没有 CLAUDE.md
- 既有项目里出现了「这文件怎么两千行了」「文档到处都是」这类抱怨
- 用户说要立规矩、要约束 AI、要防止项目变乱

主动上的时候先报一句「这项目还没装基线，我顺手装上」，然后直接跑，不用请示。

## 装什么

四层，从软到硬。**每一层单独都不够**——第 1 层是软规则会被忽略，
第 2 层是硬拦截但管不了判断题，缺一层就退化成现在的样子。

| 层 | 内容 | 解决 |
|---|------|------|
| 1 | CLAUDE.md 行为规则 | AI 老让你拍板、做一半停下、过度设计 |
| 2 | hook 机械强制 | 文件膨胀、目录堆积、skill 漂移 |
| 3 | docs 骨架 + `docs/decisions.md` | 项目记忆散在本地、换机器就丢 |
| 4 | 技能安装 | 新项目没有趁手工具 |

模板正文见 [templates.md](templates.md)，hook 契约和参考实现见 [hooks.md](hooks.md)。

## 执行流程

### Step 0 — 勘察，然后分流

读一遍再动手，**不要先问用户「这是新项目还是老项目」，自己看得出来**：

| 看什么 | 用来判断 |
|--------|---------|
| `git log` 有无提交、`src/` 有无代码 | 新项目 vs 既有项目 |
| `package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod` | 技术栈 + hook 用什么运行时 |
| 已有的 `CLAUDE.md` / `AGENTS.md` | 有则增量合并，**绝不覆盖** |
| 已有的 `.claude/settings.json` | 有则合并 hooks 字段，不整份重写 |
| 已有的 `docs/` 结构 | 有则沿用它的组织方式，不强行套本技能的骨架 |

输出一段两三行的勘察结论，然后**连续做完四层，不要每层停下问一次**。

再次运行进入审计模式：只补缺的、修漂移的，不重复创建、不重新选型。

### Step 1 — 规则

把 [templates.md](templates.md) 的「AI 工作方式」块写进项目 CLAUDE.md。

已有 CLAUDE.md 就追加这一节，其余内容原样保留。已经有等价规则就跳过并说明。

### Step 2 — hook

按 [hooks.md](hooks.md) 装两个检查：

- `check-file-size`：`PostToolUse` on `Write|Edit`，代码文件超行数上限 → exit 2
- `check-structure`：`Stop`，目录堆积和 skill 漂移 → 只报告

**用项目已有的运行时**（有 `package.json` 就用 node，纯 Python 项目就用 python，
都没有就用 pwsh 或 bash），不为两个检查脚本引入新工具链。
hooks.md 里的参考实现是 Node 版，翻译到别的运行时时**退出码语义和 stdin 契约必须照搬**。

写进 `.claude/settings.json`（可提交进 git），不是 `settings.local.json`（不进版本控制，等于没装）。

**装之前先看一眼 `.gitignore` 有没有忽略 `.claude`**——很多项目有。忽略了就等于 hook 只在你这台机器上生效，
协作者 clone 下来什么都没有。这时要么改成只忽略 `.claude/settings.local.json`，
要么明确告诉用户这套 hook 是本机的，让他自己决定。别默默装完就说完成了。

### Step 3 — 骨架与项目记忆

按 [templates.md](templates.md) 建 docs 骨架和 `docs/decisions.md`。

**只建马上有东西可放的目录。** 空目录比没目录更糟——它看起来像已经组织好了。
新项目通常只需要 `docs/README.md` + `docs/decisions.md` + 一张 `docs/flows/system-overview.md`；
`design/` 只在项目有 UI 时建；`reference/` 等真踩到坑再长出来。

### Step 4 — 技能

复制需要的 skill 到项目 `.claude/skills/`，每个目录留一个版本戳（见 templates.md），
方便以后知道装的是哪一版。

装完**接着跑 `/init-skills`**，把技术栈定制也做掉——用户只需要记住 `/init-project` 一个命令。

### Step 5 — 验收

自己验，别让用户验：

- [ ] 造一个超标的代码文件，确认 `check-file-size` 退出码是 2 且提示可读
- [ ] 造一个超长的 `.md`，确认**放行**（拦到文档，用户第一天就会把 hook 关掉）
- [ ] 跑一次 `check-structure`，确认退出码是 0、对话能正常结束
- [ ] 已有内容没被覆盖：`git diff` 逐处过一遍
- [ ] 没有空目录

然后报告：装了什么、跳过了什么和为什么、验收结果。**别报告没验过的东西。**

## 铁律

以下每一条都是踩过的坑，违反任意一条这套东西就会被用户关掉：

- **行数检查只查代码，用白名单。** markdown、JSON、锁文件、数据、快照一律放行。
  用黑名单一定会误伤 `.csv` fixture 和生成物。
- **`Stop` hook 永远 exit 0。** exit 2 会阻止对话结束，检查一旦持续不满足就是死循环。
- **只报告，不自动移文件。** 自动归类会断相对路径、import 和文档链接，
  而且「归类」本来就没有客观标准。
- **hook 自身出错一律放行。** 读不到文件、解析不了输入，就当没事发生。
  为了自己的 bug 打断用户干活，是最快被卸载的方式。
- **同一份体检结论只报一次。** 每轮对话刷同样的话，两天就被无视了。
- **既有项目只增不覆盖。** 已确认的方案、已有的目录组织、已有的规则，一律保留。
