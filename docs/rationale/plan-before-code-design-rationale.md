# 先设计后编码：为什么 AI 写代码前必须先画图

> 作者：Joey Liu
> 日期：2026-04-07
> 背景：在全程使用 AI 辅助开发的实践中，发现 AI 代码质量问题的根源不在"写"而在"想"。本文整理了发现过程、分析和解法。

---

## 问题发现

### AI 写的代码为什么总是不完善？

全程用 AI 写代码后，两个问题反复出现：

**问题一：架构混乱，样式不统一**

AI 没有"全局记忆"。每次对话它只看到当前上下文：

- 第一次对话写了一个 Button 组件，第二次对话不知道，于是又造了一个
- 今天用 `gap-4`，明天用 `margin: 16px`，后天用 `space-y-4`
- 文件越来越大——AI 倾向于"在现有文件里加"而不是"拆出去"
- 没有设计系统，想到什么写什么，每次对话的设计产出都不一样

**问题二：逻辑不完善，交互有问题**

AI 写代码是"局部最优"的——它把你描述的功能实现了，但不知道这个功能和其他功能之间的边界在哪：

- 你说"做一个上传功能"，它做了，但没考虑上传中途取消怎么办
- 你说"加一个删除按钮"，它加了，但没想到删除后列表需要刷新
- 表单提交的 loading、error、empty 状态——AI 经常只实现 happy path
- 功能和功能之间的交界处总是出问题

### 根因分析

这两个问题的根因是同一个：**AI 跳过了设计阶段直接写代码。**

AI 出现之后，很多人以为描述一下需求就能直接出完整代码——这个预期本身就是错的。传统开发流程是：需求 → 设计 → 开发 → 测试。AI 让"开发"变便宜了，但让人产生了一个错觉：设计也可以跳过。

实际上，AI 越强，**设计阶段越重要**。因为实现变便宜之后，错误的设计带来的返工成本才是主要成本。

---

## 解法：先设计后编码

### 核心思路

在 AI 写任何代码之前，强制它先输出：
1. 架构图——模块怎么拆、谁依赖谁
2. 流程图——用户走什么路径、状态怎么转换
3. 边界清单——什么地方会出问题

用户审核这些设计产出，确认没问题后，AI 才开始写代码。

### 为什么这样做有效

**改流程图一行字 = 改代码半小时。** 设计阶段是最廉价的 debug——你在审核流程图的时候，其实在做成本最低的问题排查。发现漏掉的分支，改一行文字就行；等到代码写完再发现，可能要重构半天。

这不是什么新发明，而是**回归软件工程的本质**。需求 → 设计 → 实现 → 验证，这个流程几十年来一直有效。AI 没有改变这个事实，只是让"实现"这一步变快了。

### 但流程图本身也有局限

一个关键洞察：**如果你对某个功能的边界 case 本身就没想到，流程图也看不出缺了什么。**

流程图只是把 AI 的理解可视化了。AI 漏掉的东西，流程图里也不会有。

所以光画流程图不够。还需要一个**强制枚举边界的环节**——不是让 AI 画它想到的，而是按方向逼它检查：中断了怎么办？数据为空怎么办？网络断了怎么办？并发了怎么办？

---

## 三阶段设计的核心机制

每个阶段都在对抗 AI 的某个默认行为：

| 阶段 | 打破的默认行为 | 本质作用 |
|------|--------------|---------|
| **架构骨架** | 一个文件写到底 | 强制先想清楚模块拆分和依赖关系，给 AI 一个结构去填充 |
| **流程与状态** | 只想 happy path | 用 Mermaid 图把所有路径（含异常）可视化，遗漏无处可藏 |
| **边界清单** | 流程图也只画想到的 | 按 7 个方向强制枚举，把"没想到"变成"想过但不适用" |

### 为什么是三阶段而不是一次性全出？

**用户在每个阶段之间审核。** 架构图有问题，Phase 1 就打回去——省掉了 Phase 2 和 Phase 3 的全部工作。这是**门控式设计**：越早发现问题，修正成本越低。

### 骨架优于规则

另一个关键思路：与其告诉 AI"禁止单文件超过 300 行"，不如**给它一个已经存在的架构骨架**。

- 先把目录结构想好，模块职责定好
- AI 的任务从"从零开始写"变成"往骨架里填肉"
- 这和"方向而非枷锁"的 skill 设计哲学一脉相承——不是告诉它"不许做什么"，而是给它一个结构让它在里面工作

---

## 边界清单的 7 个方向

为什么用"方向"而不是"逐条清单"？因为遵循"方向而非枷锁"原则——告诉 AI 往哪看，而不是每一步怎么做。

| 方向 | AI 应关注的内容 |
|------|----------------|
| **中断** | 用户取消、离开页面、刷新、关闭标签 |
| **空值/缺失** | 无数据、首次使用、已删除内容、过期会话 |
| **错误状态** | 网络失败、API 错误、超时、权限不足 |
| **并发** | 双击、并行请求、过期数据、乐观更新 |
| **规模** | 0/1/100/10000 条数据时的表现 |
| **跨功能** | 新功能与现有功能在边界处的交互 |
| **状态转换** | 状态机每个入口/出口是否完整、有无死锁 |

这 7 个方向不是清单——AI 不需要对每个方向都列 5 条。它应该根据具体任务判断哪些方向最关键，深入那些方向。

## 与 triple-check 的关系

plan-before-code 和 triple-check 是互补的，覆盖不同阶段：

```
plan-before-code（设计阶段）→ triple-check（实现阶段）→ code-review（审查阶段）
```

- **plan-before-code** 解决"写什么"——架构、流程、边界都想清楚
- **triple-check** 解决"写得好不好"——三轮自纠，确保实现质量
- 两者结合：先设计后实现，每个模块用 triple-check 高质量交付

plan-before-code 的设计文档输出包含实现计划（模块顺序 + 依赖），可以直接逐个交给 `/triple-check` 实现。

## 弱点与风险

**不是银弹**：

- **过度设计**：简单任务（改个 bug、加个按钮）不需要三阶段设计文档
- **设计与实现脱节**：写代码时发现设计有问题是正常的，设计文档不应该成为枷锁
- **增加沟通成本**：三个阶段的审核需要用户投入注意力
- **Token 消耗**：设计文档留在上下文中，会占用后续实现的 token 空间

**成瘾风险**：

- 用户习惯"反正 AI 会先设计"后，可能自己不再思考架构
- 审核设计文档需要架构判断力——如果用户对边界 case 本身不熟悉，审核也看不出问题

**权衡**：节省的是**返工时间**（设计阶段改一行 vs 代码阶段改半天），代价是**前期投入**（多花几分钟审核设计）。对中大型功能来说，这笔交易通常很划算。
