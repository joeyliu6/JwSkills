# Skill 设计哲学：方向而非枷锁

> 作者：Joey Liu
> 日期：2026-04-06
> 背景：在编写和迭代 Koda 过程中，通过 AI 采访式对话 + 实际使用反馈沉淀出的设计原则。

---

## 核心发现

### AI 采访产出很好，但"总结成规则"会变味

一个反复出现的模式：

1. **AI 采访我**，通过问答理解我的需求、偏好、痛点
2. **对话过程中**的产出质量极高——AI 能灵活理解上下文，自然地做出好判断
3. **让 AI 把这些对话总结成 Skill** 时，它倾向于列出一长串"应该做什么"和"不该做什么"
4. **这些规则反过来束缚了 AI**——产出变得死板，像戴了枷锁

问题在于：对话中的洞察是**鲜活的判断力**，而规则列表是**僵死的条目**。AI 在执行时变成了"逐条检查清单"而非"理解意图后灵活应对"。

### 规则越多，产出越差的悖论

直觉上，规则越详细 AI 应该越精准。但实际体验是相反的：

- **规则少**（3-5 条方向性指引）：AI 像一个拿到方向的高手，自由发挥
- **规则多**（20-30 条具体条目）：AI 变成一个逐条打勾的实习生，注意力被分散
- **规则特别多**（50+ 条）：AI 开始遗漏、矛盾、或机械地套用规则

这和人类的经验一致——给资深工程师一个方向，他能做出好东西；给他一本 200 页的规范手册，他反而束手束脚。

## 设计原则

### 原则一：只写 AI 推断不出来的东西

AI 已经知道的通用最佳实践（如"Vue 的 ref 解构会丢响应性"、"TypeScript 要避免 any"）**不需要写进 Skill**。它的训练数据里已经有了。

需要写的是：
- **项目特有约定**：你的项目用哪个 UI 库、CSS 方案、命名风格
- **非显而易见的决策**：为什么选了某个方案、有哪些历史包袱
- **团队共识**：代码评审看什么、什么程度算"够好"

**判断标准**：如果这条规则删掉，一个有经验的 AI 还能自己推断出来吗？能 → 不写。不能 → 写。

### 原则二：给方向，不给枷锁

好的 Skill 告诉 AI **往哪看**，而不是 **怎么做每一步**。

```
❌ 坏的写法（枷锁）：
- 检查 ref 是否被解构
- 检查 watch 的 flush 时机是否正确
- 检查 computed 是否有副作用
- 检查组件卸载时是否清理了 watch
- 检查 v-if 和 v-show 的选择是否合理
- ...

✅ 好的写法（方向）：
- 关注 Vue 3 响应性正确性和组件清理
```

AI 看到"关注 Vue 3 响应性"，会自动想到 ref 解构、watch 时机、computed 副作用等——因为它已经知道这些。你只需要告诉它"这个项目用 Vue 3，所以这个方向需要关注"。

### 原则三：Skill 是知识，不是流程监控

Claude 官方把 Skill 分为两类：
- **知识型**（Reference）：给 AI 补充它不知道的信息
- **任务型**（Task）：给 AI 明确的执行步骤

大多数好的 Skill 应该偏向知识型。即使是任务型（如 triple-check 的三轮流程），核心价值也在于"强制走三遍"这个**结构**，而不是每一步的具体检查条目。

### 原则四：信任 AI 的能力

写 Skill 时容易陷入一个心态：不把每个细节都写清楚，AI 就会遗漏。

但实际上 AI 的能力很强——它知道各种框架的陷阱、各种语言的最佳实践、各种设计模式的优劣。你需要做的不是教它这些，而是：

1. 告诉它**你的项目具体用了什么**（技术栈、约定）
2. 告诉它**你特别在意什么**（信噪比、不要误报、等）
3. 让它**自由发挥**

## 实践指南

### Skill 编写检查清单

写完一个 Skill 后，逐条审视：

1. **SKILL.md 超过 500 行了吗？** → 拆分，详细内容放辅助文件
2. **有多少条规则？** → 超过 15 条就要警惕。能合并的合并，能删的删
3. **删掉某条规则后，AI 还能自己做对吗？** → 能 → 删掉
4. **规则是"方向"还是"步骤"？** → 尽量写成方向
5. **有没有在教 AI 它已经知道的东西？** → 有 → 删掉

### 从对话到 Skill 的正确流程

1. **AI 采访你**，产出高质量对话内容
2. **提炼核心洞察**，而非逐条总结
3. 问自己：这次对话中，**什么是 AI 自己推断不出来的？** 只保留这部分
4. 用**方向性语言**写成 Skill，不要列清单
5. 测试：Skill 加持下的 AI 产出，是否比**无 Skill 但给了同样方向的一句话**更好？如果差不多，说明 Skill 的价值不大

### 何时需要详细规则

并非所有场景都适合"方向而非枷锁"：

- **安全相关**：安全检查清单值得详细列出，因为遗漏的代价极高
- **强制流程**：如 triple-check 的三轮结构，这个"骨架"需要明确
- **项目特有禁忌**：如"绝对不要直接操作数据库"，这类 AI 推断不出来的硬性约束

关键区分：**结构和方向要明确，具体执行留给 AI 判断。**

## 与 Claude 官方指南的对照

| 官方建议 | 本文理解 |
|----------|---------|
| SKILL.md 控制在 500 行以内 | 500 行还嫌多——大多数好 Skill 在 100-200 行 |
| Description 前置关键用途，250 字符上限 | 用一句话说清"什么时候用"，多一个字都是噪音 |
| 详细参考放辅助文件 | 辅助文件是"需要时才看"的百科，不是"每次都加载"的规则 |
| 知识型 vs 任务型 | 大多数 Skill 应偏向知识型，任务型只定结构不定细节 |
| 支持子代理执行（`context: fork`） | 复杂任务隔离执行，避免污染主对话 |

---

## 总结

**一个好的 Skill = 一句方向 + AI 自身能力。**

不要把 Skill 当成规范手册来写。把它当成你对一个聪明同事说的一句话：

> "这个项目用 Vue 3 + PrimeVue，我们比较在意性能和无障碍，CSS 用变量不要硬编码颜色。"

这一句话比 50 条规则更有力量。
