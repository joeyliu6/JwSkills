# 软件开发 SOP：五层结构与待补的两层

> **这是路线图，不是现状。** 第 3、4 节描述的两个技能**尚未实现**，
> 本文只定义它们要解决什么、边界在哪。读到这里的 AI 不要假设它们存在。

---

## 1. SOP 的五层

一套 AI 协作 SOP 由五层构成，缺任何一层都会在不同的时间尺度上失效：

| 层 | 回答什么 | Koda 现状 |
|---|---|---|
| **宪法** | 这个项目的硬规矩 | `CLAUDE.md` + `init-project` 装进新项目 ✅ |
| **工作流** | 具体一件事怎么做 | 8 个技能 ✅ |
| **闸门** | 可机械判定的部分谁来卡 | 行数 hook、结构 hook ✅ |
| **记忆** | 为什么这么定 | `docs/decisions.md` ⚠️ 弱 |
| **减法** | 防止上面四层自己长胖 | ❌ 无 |

按生命周期铺开，工作流层的覆盖是这样的：

```
装规则 → 方案讨论 → 设计 → 实现 → 审查 → ？
init-project  huxun   plan-   triple-  code-
init-skills           before-  check   review
                      code
                                              ↑
                        summon（贯穿）    这里断了
                        create-skill（元）
```

断在两处：**代码写完之后没人做减法**，**文字质量全程无人管**。

---

## 2. 为什么偏偏是这两层

其它能力缺了，只是当下少做一件事。这两个缺了，**项目会随时间恶化**——
这是唯一的区别，也是它们值得优先补的全部理由。

### 膨胀是单调的

AI 只会加，不会减。每次对话它都倾向于新增文件、新增配置项、
新增"以后可能用得上"的抽象。没有反向力量，代码、文档、规则三条线同时单调增长。

跑一年之后的典型状态：CLAUDE.md 三百行没人读完，
`docs/` 里一半文档描述的是已经不存在的东西，
`src/` 里有若干个只有测试在调用的模块。**这时 SOP 已经死了**——
因为 AI 读不完，也就不再遵守。

膨胀的三条线要一起管：

| 线 | 症状 |
|---|---|
| 代码 | 没有生产消费者的模块、只被测试调用的 API、投机性的通用化 |
| 文档 | 描述已不存在事物的段落、同一事实的多个副本、空壳目录 |
| **规则自身** | CLAUDE.md 越写越长、技能越加越多、每条都"看起来有用" |

第三条最容易被漏掉，也最致命：**减法机制必须能管到 SOP 自己。**

### 文字没有编译器兜底

代码写错，编译器和测试会报错。文字写歪，没有任何东西会报错——
而文字恰恰是**下一个 AI 的输入**。

中文提示词 + AI 写文档，产出的注释和文档几乎必然带着"当时那次会话"的视角：

```
// 根据你的要求改成了异步
// 这里之前有个 bug，现在修好了
// 按照之前讨论的方案，先检查再创建
```

三句都是**站在会话里说话**，不是站在仓库里说话。下一个 AI 读到时：
"你的要求"是谁的要求？"之前"是什么时候？"讨论的方案"在哪？
**每一个引用都解析不了，但每一句读起来都像事实。**

判别式（借自 DeepSeek 的 `dsh-trim-cot-leakage`，见[拆解](guides/dsh-skills-teardown.md#一dsh-trim-cot-leakage全场最原创)）：

> 一个站在当前代码、**没有任何会话记录**的读者，
> 能不能解析每一个引用、验证每一个论断？

## 3. 减法层（待建）

**技能名候选**：`slim`（推荐，与 `code-review` / `plan-before-code` 的英文风格一致）。

### 要做什么

按三条线找候选，**产出提案，不直接动手**。

删除属于 CLAUDE.md 里"必须停下问"的第 4 类（不可逆操作），
所以这个技能的产出是一份带证据的清单，逐条等确认——
**这一条不能松，否则它就成了整套 SOP 里最危险的技能。**

### 强候选的定义

有证据表明**当前的东西成本超过它买到的价值**：

- 某模块/函数/配置项**没有生产调用者**（只有测试或文档在引用）
- 两处代码或两段文档镜像同一个事实
- 某个特例分支、回滚路径、防御性检查只是为了保护一个没人用的接口
- 投机性通用化：为"以后可能"建的抽象层、配置项、扩展点，**至今没有第二个使用者**
- 文档描述的东西在代码里已经不存在
- 手写代码重造了成熟依赖或语言内置已有的能力

### 弱候选（不值得提）

删一个错字、跑一次死代码检测工具、
以及**没有调用点证据的"这看起来很复杂"**。

### 红线：不许动的

**有意的冗余不是浪费。** AI 最容易犯的错就是把设计里刻意保留的东西当成垃圾：

- 有文档或 `decisions.md` 明确说明理由的设计
- 成对存在的东西（双实现、双后端、正反测试）——默认有意，除非明确推翻
- 为了兼容性、安全边界、失败模式而存在的代码

**给减法本身划红线，和给减法定标准同等重要。**

### 方法论

分类调用者再动手：**生产语料**（真正跑起来的代码和配置）
vs **非生产语料**（测试、文档、注释、示例）。
先全文搜索，然后**读调用点**——工具能给候选，不能替代理解。

### 触发时机

不做定期审计（没人会记得）。绑在两个自然发生的动作上：

- 用户说"清理一下"、"这里是不是有点乱"、"精简"
- **完成一个功能之后**——刚加完东西是最容易看出加多了的时候

## 4. 文字质量层（待建）

**技能名候选**：`prose`（推荐）。

### 管什么

代码注释、文档、README、commit message——所有会被下一个 AI 读到的文字。

### 核心判别式

第 2 节那条"HEAD 读者测试"。答不能，就要改。

### 常见的四类（按中文 AI 开发的实际频率排）

| 类 | 长什么样 | 怎么改 |
|---|---|---|
| **会话视角** | "根据你的要求"、"按之前讨论的"、"这里之前有个 bug" | 陈述当前行为，删掉来路 |
| **变更叙述** | "原来是 X 现在改成了 Y"、"不再使用"、"已废弃的旧写法" | 只说现在是什么；变更历史 git 里有 |
| **对评审者辩护** | "这个转换是安全的，因为它只是…"、"这样写是对的" | 陈述那个让它安全的**不变量**，或者删掉 |
| **控制流复述** | "先检查登录，然后查库存，最后创建订单" | 删；代码已经这么写了 |

第三类最隐蔽：**一段注释在论证自己正确，说明它在对评审者说话，不是对维护者说话。**

### 修法不是一删了之

带有事实子句的段落，要**先把事实重述成脱离会话也成立的形式**，再删掉周围的叙述。
只有完全不含事实的（纯控制流复述）才直接删。

删之前先列出这段话里的每个命题：行为者与动作、条件与顺序、
情态（必须/可以/绝不）、**负向保证与例外**、失败模式与后果。
**每一个事实子句都存活，删减才算改进——字数变少本身不是改进。**

### 反向清单：这些不算问题，别改

防止过度纠正（改坏比不改贵）：

- issue / PR 编号引用——它们在仓库里解析得了
- `eslint-disable -- 理由`、空 catch 的说明——这类是**必需**的文字，理由写错要修正，不能删
- 反事实锚点："没有这个检查，并发时会重复扣款"——这是回归防线，不是历史
- 实测数据："实测 512 层嵌套约 0.15 秒"——"实测"这个词是承重的
- 运行时的新旧状态："旧连接排空后新连接才接受"——这是生命周期，不是变更历史

### 触发时机

绑在写完文档或注释之后，以及 `code-review` 里作为一个维度。
**不做全仓库定期扫描**——成本高且没人会记得跑。

## 5. 防止 SOP 自己膨胀

减法技能的审查范围**包括 CLAUDE.md 和 `skills/` 本身**。这是整套设计的闭环。

另外两条约束，写进将来的实践里：

**技能的入场费。** 每加一个技能，问一句：
它解决的是"当下少做一件事"，还是"不补就会随时间恶化"？
前者可以不加。DeepSeek 有 11 个技能是因为他们有 30 条 conventions 和一套 CI 闸门要伺候；
Koda 的技能是分发单元，数量上去了用户根本不知道该用哪个。

**CLAUDE.md 的行数。** 现在 [CLAUDE.md](../CLAUDE.md) 已经有文档表 + 技能表 + 双目录规则，
每加一个技能就多一行。超出一屏之后开始稀释——
处理顺序是**重新安置 → 压缩 → 才考虑放宽**，不要一上来就往里塞。

---

## 6. 暂缓：提交前验证

DeepSeek 有 `dsh-pre-push-checks`，反制 AI 用"跑全套测试"表演尽责。
Koda 暂不补，两个理由：

1. 现有的行数 hook 和结构 hook 已经覆盖了机械检查那部分
2. "选最小验证集"高度依赖具体项目的测试组织方式，
   通用技能写出来只会是正确的废话——**这正是 SOP 通用化的核心张力**

将来要补的话，正确的位置是 `init-skills` 生成的 project-config.md，
而不是一个新技能。

---

## 7. 实践顺序

先 `slim`，后 `prose`。理由：膨胀是复利的，越早有反向力量越省事；
文字质量的损失是线性的，晚补一阵子代价可控。

两个都建成之后，回头看 `decisions.md` 要不要升级
（三档方案见 [agent-notes-guide.md 落地档位](guides/agent-notes-guide.md#落地档位)）——
到那时才有足够的实际使用经验判断单文件表格够不够用。
